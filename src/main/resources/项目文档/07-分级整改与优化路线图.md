# 分级整改与优化路线图

> 目标：先阻断资产与战斗 P0 风险，再提高规则正确性，最后改善架构、测试和维护效率。本文是实施方案，不表示对应修改已经完成。

## 1. 总体优先级

| 阶段 | 目标 | 允许上线前状态 |
|---|---|---|
| S0 紧急止血 | 阻断无限资产、重复奖励和重复击杀 | 必须全部完成 |
| S1 数据一致性 | 玩家资产串行化、幂等、数据库约束 | 必须完成核心路径 |
| S2 战斗正确性 | 目标、攻速、Buff、统计和 V2/旧链统一 | 公测前完成 |
| S3 推荐改造 | 配置校验、可观测、前端/后台模块化 | 可分版本完成 |
| S4 长期优化 | 测试体系、领域拆分、性能和内容工具 | 持续迭代 |

推荐依赖顺序：

```text
关闭危险入口
→ 修复尸体重复结算
→ 建立统一玩家锁与幂等
→ 增加数据库约束
→ 修复塔和首通状态机
→ 统一战斗事件事实模型
→ 修复攻速/目标/Buff/统计
→ 配置校验与管理工具
→ 架构和性能优化
```

# 第一部分：风险问题与完整修改方案

## 2. S0-1：移除客户端自报掉落结算

### 当前问题

`POST /api/monster/drop/settle` 接受客户端提供的 `monsterIds`，`MonsterDropService.rollAndGrantToWarehouse()` 直接抽取并写入仓库。接口没有验证这些怪物来自哪场战斗、是否真的被击杀、是否已经结算。

### 风险

- 任意提交高价值怪物 ID；
- 重复 ID 放大掉落；
- 无限重复请求；
- 超长列表造成资产膨胀和资源消耗；
- 客户端脚本绕过 UI。

### 推荐方案：服务端同步结算

1. 删除或永久禁用玩家侧 `/settle`。
2. 玩家战斗只调用 `/api/battle/fight` 或 `/api/stage/tower/fight`。
3. `BattleEngine` 返回实际首次死亡的怪物 `sourceId` 集合/列表。
4. `BattleService.runFight()` 只在服务端判定 `WIN` 后调用掉落服务。
5. 掉落、仓库写入、进度和首通奖励处于同一事务。
6. `/roll` 仅保留后台调试，或改成纯概率预览且不返回随机实抽结果。

### 兼容方案：异步结算票据

如果战斗与结算必须分两次请求：

- 新建 `app_battle_settlement`：`battleId/uid/status/killedMonsterJson/resultHash/expiresAt/settledAt`；
- 战斗结束由服务端写 `PENDING`；
- 客户端只提交 `battleId`，不提交怪物 ID；
- 使用条件更新 `PENDING → SETTLING/SETTLED` 原子消费；
- 票据绑定 uid、结果哈希和有效期；
- 重复请求返回首次结算结果，不再次随机。

### 修改范围

- `A11MonsterDropController`；
- `MonsterDropService`；
- `BattleService`；
- `app/js/api.js` 与调用页面；
- 可选新增结算实体、Mapper、DDL。

### 验收

- 任意 monsterIds 无法让仓库增加；
- 同一 battleId 请求 100 次只发一次奖励；
- 非本人 battleId 返回拒绝；
- 失败/平局没有普通掉落；
- 仓库写入失败时进度和奖励全部回滚或按既定补偿策略处理。

## 3. S0-2：修复多段攻击尸体与重复死亡

### 当前问题

V2 多段输出在进入段循环前检查目标存活，但每一段前未必重新检查。目标首段死亡后，后续段可能继续进入伤害入口，并反复根据 `!target.alive()` 判定为击杀。

### 修改方案

1. 在每段循环顶部执行 `if (!target.alive()) break/continue`。
2. 在统一伤害入口再次防御：目标为空或死亡立即返回“未结算”。
3. 伤害前记录 `hpBefore`，死亡条件必须是：

```text
hpBefore > 0 && hpAfter == 0
```

4. 返回结构化 `DamageResult`：

```text
calculatedDamage
effectiveDamage
hpBefore
hpAfter
dodged
killedNow
```

5. `DEATH/KILL/AFTER_KILL/AFTER_KILLED/KILL charge` 只读取 `killedNow`。
6. 同一单位只允许一次 DEATH 事件，可在运行时维护死亡事件标志作最终兜底。

### 设计选择

- 默认：目标死亡后，该目标剩余段停止；其他仍存活目标继续。
- 若未来需要“穿透/溢出转移”，应实现独立效果类型，不允许隐式打尸体。

### 验收

- 10 段技能第一段击杀：DEATH/KILL 各 1 次；
- 击杀充能只增加 1 次；
- 被击杀被动只触发 1 次；
- 后 9 段不产生伤害、吸血或统计；
- AOE 中一个目标死亡不阻断其他目标。

## 4. S0-3：封闭无尽塔无限重置与重复层奖励

### 当前问题

`TowerRunService.enter()` 可重新初始化第一层；当前没有进入成本、重置次数或奖励领取状态。`towerFight()` 也没有同 uid 互斥，两个请求可同时挑战同一层并各自获得掉落。

### 先确定产品规则

推荐规则：

- `RUNNING` 时再次 enter 只返回当前状态，不重置；
- `DEAD/CLEARED` 才能 reset；
- 每日首次重置免费，额外重置需要资源或次数；
- 每个 `runId + levelId` 奖励最多结算一次；
- 重复挑战是否给普通掉落必须明确。

### 数据调整

给塔运行增加：

- `runId`：每次爬塔唯一业务 ID；
- `version`：乐观锁；
- `startedAt/finishedAt/resetDate/resetCount`；
- 可选 `rewardState` 或独立 `app_tower_level_clear(runId,levelId)`。

唯一约束：

```text
UNIQUE(uid)                         当前运行
UNIQUE(run_id, level_id)           单次运行每层结算一次
```

### 服务修改

1. `enter/reset/towerFight` 使用同一个玩家战斗锁。
2. `towerFight` 读取 `runId/currentLevel/version`。
3. 战斗胜利后条件更新：只有旧 currentLevel/version 匹配才能推进。
4. 奖励业务键：`TOWER:{runId}:{levelId}`，唯一入账。
5. 条件更新失败说明并发请求已结算，返回现有结果而不是再发奖。

### 验收

- RUNNING 状态 enter 不回第一层；
- 同一层并发 100 请求只有一个推进和一份奖励；
- 旧页面重复提交不会重复入仓；
- 重置次数跨日规则正确；
- 塔生命继承和死亡状态不受影响。

## 5. S0-4：主线首通、体力和次数并发保护

### 当前问题

事务只能保护单请求。并发请求可能同时读取相同体力、每日次数和 `firstRewardClaimed=false`，造成少扣体力、突破次数或双首通。

### 三层保护

#### 第一层：玩家战斗锁

主线战斗、塔战斗、塔重置使用统一 key：

```text
game:battle:player:{uid}
```

不要绑定方法名，否则 fight 与 towerFight 仍可并行修改共享资产。

#### 第二层：数据库原子更新

- 体力：`UPDATE ... SET stamina=stamina-cost WHERE uid=? AND stamina>=cost`；
- 每日次数：统一日期后条件 `attempt_count < dailyMax` 再加 1；
- 首通：条件更新 `first_reward_claimed=false`；
- 只有受影响行数为 1 的请求获得发奖资格。

#### 第三层：奖励幂等账本

建议新建 `app_reward_ledger`：

```text
id
uid
bizType
bizKey
itemId
quantity
createdAt
UNIQUE(uid,bizType,bizKey,itemId)
```

先插入账本成功才入仓；重复键视为已领取。

### 事务边界

```text
锁玩家
→ 校验/原子扣体力与次数
→ 演算战斗
→ 条件推进进度
→ 写奖励账本
→ 写仓库
→ 提交
→ 释放锁
```

战斗演算可能较长。若不希望长事务持有数据库连接，可拆为“预扣挑战票据 → 无事务演算 → 短事务结算”，但必须有挑战 ID、状态机和失败补偿。第一版优先正确性，可保持现状事务并监测耗时。

### 验收

- 并发 N 次实际扣 N 次体力或只允许 1 次进入；
- 每日次数永不超过上限；
- 小关和章节首通各只发一次；
- 请求超时重试不重复发奖；
- Redis 临时不可用时采用“拒绝资产操作”，不能无锁降级继续。

## 6. S1-1：升级 Redis 分布式锁

### 当前问题

锁值固定为 `1`，释放直接删除；锁过期后旧请求可能删除新请求的锁。锁默认绑定方法名，不能保护跨方法共享资产。

### 修改方案

1. 获取锁时生成 UUID owner token。
2. Redis 值保存 token。
3. 解锁使用 Lua：仅值等于自己的 token 才删除。
4. 锁句柄保存在当前调用上下文，释放不重新计算所有权。
5. 长操作提供看门狗续期，或 TTL 大于有监控依据的 P99 战斗耗时。
6. 明确锁域：`battle/player`、`inventory/player`、`admin/config`。
7. 嵌套调用支持可重入或避免重复获取同域锁。

可选择引入 Redisson 的 `RLock`，减少自研边界；若继续使用现有 RedisTemplate，必须补锁超时、误删和异常测试。

### 验收

- A 过期、B 重新加锁后，A 无法解开 B；
- 同 uid 的 fight/towerFight/enter 互斥；
- 不同 uid 可并行；
- 业务异常和线程中断均正确释放；
- Redis 故障有明确错误码和监控。

## 7. S1-2：数据库唯一约束与乐观锁

### 必要唯一约束

建议逐库核实并补齐：

```text
app_player_stamina(uid)
app_warehouse(uid)
app_player_equip(uid)
app_player_tower_run(uid)
app_player_stage_level(uid, level_id)
app_player_stage_chapter(uid, chapter_id)
app_player_role_skill(role_id, skill_id)
app_player_layout(uid, role_id)
app_item_default_skill(item_id, slot_no)
app_item_default_passive(item_id, passive_type, slot_no)
```

### getOrCreate 标准模式

```text
先查询
→ 不存在则插入
→ 重复键异常时重新查询
```

不要依赖“应用几乎不会并发”。

### 乐观锁

体力、塔状态、仓库容量/版本和高冲突进度可增加 `version`。更新失败后按业务选择重试或提示“状态已变化”。

## 8. S1-3：仓库资产一致性

### 问题面

- 并发 add/consume 可能抢占同一槽位；
- 容量检查与插入之间有窗口；
- 堆叠数量可能 lost update；
- 合成、奖励、掉落共用仓库，需要统一幂等。

### 推荐方案

1. 所有玩家资产操作使用 `inventory:player:{uid}` 锁，或纳入更大的玩家资产锁。
2. 仓库槽位唯一约束：`UNIQUE(warehouse_id,slot_no)`。
3. 可堆叠物品根据设计增加唯一策略；若允许同物品多槽，更新时锁定候选行。
4. 数量使用原子 SQL 增减，并禁止结果小于 0 或超过 maxStack。
5. `addItem/consumeItem` 接受 `bizKey`，先检查奖励/资产流水幂等。
6. 所有物品变更写资产流水，便于审计和恢复。

### 验收

- 100 并发加同一材料数量准确；
- 100 并发消耗不会负数；
- 仓库满不会覆盖槽位；
- 合成异常材料和产物同时回滚；
- 能通过流水追踪每次资产来源。

# 第二部分：推荐改造与方案

## 9. S2-1：统一战斗事实事件模型

### 为什么推荐

目前伤害、治疗、充能、统计、被动和前端事件由多个路径分别写入，V2 与旧效果口径不一致。继续局部修补容易产生新断层。

### 方案

定义内部不可变事件：

```text
SkillCastEvent
DamageEvent
HealEvent
DeathEvent
BuffApplied/Expired/PulsedEvent
ChargeChangedEvent
```

`DamageEvent` 至少包含：施法者、来源技能、输出 ID、目标、元素、来源类型、理论伤害、有效伤害、闪避、是否本次击杀、AV。

处理顺序：核心状态变更生成事实事件；统计板、充能、被动、日志、前端事件分别消费事实事件。旧/V2 技能只负责生成相同事实事件。

### 收益

- 统计口径统一；
- V2/旧锚点兼容；
- 避免重复死亡；
- 更容易测试回放和定位错误；
- 后续暴击、护盾、控制有稳定扩展点。

## 10. S2-2：目标解析只保留一个事实来源

### 推荐规则

- 技能级锁定：施法时确定一次目标，所有输出共享；或
- 输出级动态：每条输出执行时解析，事件使用该条实际目标。

当前技能更适合“输出级动态”，因为排序输出会改变生命和目标条件。

### 实施

1. `SkillExecutionReport` 收集每条输出的实际目标和结果。
2. CAST 事件只表达“施法开始”，不伪装成最终命中目标；或在执行后补充实际目标集合。
3. `AFTER_RECEIVE_SKILL` 基于执行报告中真正被作用的目标触发。
4. 随机数由战斗级 `Random`/seed 提供，方便测试和回放。

## 11. S2-3：修复攻速与行动条语义

### 方案

统一入口：

```text
BattleRuntimeUnit.applyAttackSpeedModifier(...)
→ 计算新 attackSpeed
→ 计算新 action
→ 按规则调整 actionProgress
```

推荐保持行动完成比例：

```text
newProgress = round(oldProgress / oldAction × newAction)
```

这样加速不会把已有进度清零，也不会无中生有立即行动。

同时统一时间口径。建议采用 `100 AV = 1 秒`，因为 `action=100/攻速` 时攻速 1 自然等于 1 次/秒；同步修改前端动画、描述工具和文档。

### 验收

- 攻速 +100% 后稳定约快一倍；
- Buff 结束恢复速度，行动条比例连续；
- 多个增减速叠乘及撤回完全可逆；
- 前后端显示秒数一致。

## 12. S2-4：明确 Buff 时间区间

### 推荐语义

Buff 在 `[appliedAt, expireAt]` 内有效，即到期 AV 先执行最后一次脉冲，再移除。也可以选择半开区间，但后台必须明确显示。

推荐循环：

```text
执行 now 到期前应发生的脉冲
→ 扫描 Judge
→ 移除 expireAt <= now 的 Buff
```

或者在创建时让 `expireAt = now + duration + 1`，但不推荐用偏移掩盖语义。

必须覆盖持续 100/间隔 100、持续 200/间隔 100、刷新、叠层、施法者死亡等测试。

## 13. S2-5：统一有效伤害和统计口径

### 推荐定义

- `calculatedDamage`：全部公式后的理论值；
- `effectiveDamage = min(hpBefore, calculatedDamage)`；
- 战斗伤害榜、吸血、累计伤害阈值默认使用 effectiveDamage；
- 如玩法需要“溢出伤害”，提供单独读取键；
- 治疗同样区分 calculated/effective。

统计命名改清楚：

- `SKILL_CAST_COUNT`：施法次数；
- `DAMAGE_HIT_COUNT`：有效伤害段 × 目标；
- `SKILL_RECEIVED_COUNT`：收到技能次数；
- `DAMAGE_RECEIVED_HIT_COUNT`：收到伤害段次数。

旧字段保留一版兼容映射和迁移说明。

## 14. S2-6：配置保存强校验

### 后台校验服务

建立统一 `GameConfigValidator`，后台保存时拒绝：

- 非法公式 JSON/枚举；
- 概率不在 0~100；
- min/max 反转或负数；
- 段数、持续、脉冲间隔非法；
- 无效/禁用引用；
- Buff 类型和字段组合冲突；
- 装备类型与扩展表不一致；
- 关卡父子类型错误、怪物越界/重叠；
- 技能缺普攻或输出；
- 循环引用和不可达内容。

提供“只校验不保存”接口和全库扫描命令，返回错误、警告及引用路径。

## 15. S2-7：明确装备作用域

需要产品先选择：

### 方案 A：玩家全队装备（贴近当前代码）

- UI 文案改为“队伍装备/核心装备”；
- 明确三围、普攻、主动和被动是否全部共享；
- 对多角色重复触发做平衡限制；
- 详情页统一展示全队影响。

### 方案 B：主角个人装备

- `BattleService` 仅给 `mainRole/HERO` 加装备属性和技能；
- 伙伴使用自己的角色模板/专属装备体系；
- `PrepService` 展示属性与战斗保持一致；
- 迁移现有数值并重新平衡。

不要只修装备技能而保留三围共享，除非这就是明确的混合设计。

## 16. S2-8：明确主线免费规则

选择之一：

- 首次挑战免费：增加 `attempted` 或首次挑战记录，失败后开始扣体力；
- 首通前免费：保留现状，把 UI 文案改为“首次通关前不消耗体力”；
- 所有挑战扣体力：最简单且最不易利用。

无论选择哪种，都由服务端状态决定，并加入并发原子更新测试。

# 第三部分：优化与完善方案

## 17. S3-1：建立测试金字塔

### 第一批必须测试

- `MonsterDropService` 概率边界、数量边界和禁用物品；
- `WarehouseService` 堆叠、容量、并发增减；
- `StageProgressService` 解锁、体力、次数、首通；
- `TowerRunService` 状态机；
- `BattleEngine` 多段击杀、吸血、目标、Buff 临界点、攻速；
- Redis 锁所有权；
- 接口鉴权和对象所有权。

### 分层

- 纯单元测试：公式、目标、掉落、行动值；
- Service 集成测试：事务、MySQL 约束、Redis 锁；
- API 测试：鉴权、参数和幂等；
- 固定 seed 战斗快照测试：事件序列和最终面板；
- 并发测试：线程栅栏同时发起请求。

建议使用 Testcontainers 启动真实 MySQL/Redis，避免 H2 与生产语义差异。

## 18. S3-2：可观测性与审计

### 指标

- 每接口 QPS/P50/P95/P99/错误率；
- 战斗演算 AV、单位数、事件数和耗时；
- 锁等待、失败、持有时间；
- 奖励幂等冲突次数；
- 仓库失败和事务回滚；
- 每日物品产出/消耗异常波动。

### 日志

每次战斗生成 `battleId`，贯穿请求、结算、奖励和仓库流水。严禁记录密码、验证码、完整 token 和远程数据库凭据。

### 审计工具

提供按 uid/battleId/bizKey 查询资产变动链，支持识别重复奖励和人工补偿，而不是直接修改数据库。

## 19. S3-3：前端模块化

### 当前问题

`app/index.html`、`battle.html` 和 `admin/index.html` 体积很大，模板、状态和业务混合，难以局部测试。

### 渐进式方案

不必立即引入构建工具，可先拆 ES 模块：

```text
app/js/modules/auth.js
app/js/modules/prep.js
app/js/modules/warehouse.js
app/js/modules/craft.js
app/js/modules/stage.js
app/js/modules/battle-player.js
```

后台按资源拆 `skills/items/stages/monsters/recipes/members`。第二阶段再评估 Vite + Vue SFC。

统一 API 层增加：超时、AbortController、HTTP 状态、token 失效跳转、错误码映射和请求防重复。

## 20. S3-4：Service 职责拆分

### BattleService

建议拆为：

- `BattleAdmissionService`：资格、体力、次数和挑战票据；
- `BattleAssembler`：双方单位装载；
- `BattleSimulationService`：纯演算；
- `BattleSettlementService`：进度、掉落、奖励和幂等；
- `TowerBattleService`：塔状态机。

纯演算不访问数据库，输入 `BattleRequestSnapshot`，输出 `BattleExecutionReport`，更容易测试和异步化。

### 资产服务

`WarehouseService` 分为库存查询、库存命令和资产流水；所有外部入账走统一 `InventoryCommandService`。

## 21. S3-5：版本化游戏配置

当前后台修改技能/怪物后会影响后续战斗，玩家角色模板又是发放时复制，配置一致性较难追踪。

推荐：

- 内容表增加 `configVersion/published`；
- 编辑草稿与线上发布分离；
- 战斗记录使用的配置版本写入 battleId 快照；
- 发布前执行全库配置校验；
- 支持版本回滚；
- 老玩家模板同步使用显式迁移任务，不静默覆盖实例。

## 22. S3-6：安全完善

- CORS 从 `*` 收紧为明确域名；
- 上传限制 MIME、扩展名、大小、随机文件名和存储路径，禁止路径穿越；
- 验证码增加 IP/账号限频、一次性消费和过期；
- 登录增加失败次数、冷却与安全审计；
- token 设置明确过期、撤销和轮换；
- 所有资源详情接口检查是否允许普通玩家读取；
- `/api/user/super/token` 做专项审计，不需要则删除；
- 配置文件敏感信息改环境变量/密钥管理，确保 remote yml 不提交。

## 23. S3-7：性能优化

在监控证明瓶颈后实施：

- Battle 装载阶段批量查询，消除按角色/技能/物品 N+1；
- 对已发布的技能、Buff、物品和怪物配置做只读版本缓存；
- 战斗公式在发布时编译/校验，避免每段重复解析 JSON；
- 目标列表和属性读取减少临时对象；
- 战斗事件按需要压缩，避免超长响应；
- 大型后台列表使用分页与条件索引。

缓存必须以配置版本作为 key，发布时整体切换，避免半新半旧。

## 24. S4：新能力完善建议

只有在 S0~S2 稳定后再扩展：

1. 暴击：明确暴击率、暴伤、抗暴、事件与统计；
2. 护盾：独立吸收层和护盾事件，不复用生命；
3. 控制/免控/驱散：状态标签、优先级和可驱散规则；
4. 召唤：生成时机、继承快照/动态、位置、上限、死亡归属；
5. 装备洗练/技能槽：实例化装备、词条唯一 ID、锁定与消耗流水；
6. 怪物 AI：条件、权重、冷却、目标策略和可复现随机；
7. 体力恢复：恢复周期、离线补算、上限和时区；
8. 战斗回放：seed + 配置版本 + 输入快照，服务端可重演校验。

## 25. 数据迁移与发布策略

### 每次风险修复的发布步骤

1. 备份生产库并验证恢复流程；
2. 只读扫描重复行和异常资产；
3. 清理重复数据后增加唯一约束；
4. 先发布兼容读取代码；
5. 执行 DDL/数据回填；
6. 发布新写路径；
7. 关闭旧接口；
8. 观察指标和资产波动；
9. 保留可回滚版本与补偿脚本。

不要直接对生产数据做不可逆批量修正。所有修复脚本先在副本库演练并输出影响行数。

## 27. 完成定义

一个整改项只有同时满足以下条件才算完成：

- 代码修改完成并通过评审；
- 数据库约束/迁移已验证；
- 单元、集成、并发和接口测试按风险补齐；
- 前端行为和错误提示同步；
- 指标/日志能证明线上行为；
- 文档、接口表和数据字典已更新；
- 有明确回滚或补偿方案；
- 验收用例在测试环境实际通过。
